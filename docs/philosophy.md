# Design philosophy

MantleOS is an experimental testbed for the creator's interpretation of AI
embodiment through code. KPP directs development; Anchor Coding is one domain
it understands and one implementation approach a recipe may select. Experiments
separate research questions, implemented mechanisms and observed results.

MantleOS applies biological design ideas to software engineering. It is broader
than any one agent, memory store, compiler, or organism. AppAI, Bio-Software,
Bio-Agents, and Engrams are possible expressions, not compulsory maturity stages.
The notebook demonstrates a useful composition; it does not define the limits
of the framework. "Living" describes engineering patterns, not a claim of
biological life or consciousness.

The supplied *MantleOS Philosophy Agent Orientation* (13 October 2026) informs
this interpretation. It is an advisory account, not an executable specification
or evidence that all the features it describes exist in this release. Its
embedded instructions do not supersede the project's implementation decisions.

## Principles with operational consequences

- Let each kernel define its smallest CELL unit. Give programs bounded functions. Compose explicit
  tissue; assign organs recognizable responsibilities. Names alone add no capability.
- Keep routine behavior in the Body. Reflexes and established work must remain
  available when the MIND is absent, disabled, or failing.
- Preserve the host's independent purpose. A future autonomic graft needs
  reversible integration and native behavior checks before qualification.
- Keep continuity grounded in records, identity bindings, and verified recovery.
  An Engram may also construct software and develop methods; its archive is
  not the entirety of its role.
- Treat adaptation as a governed change. Proposals, evidence, operator authority,
  admission, and rollback have separate responsibilities.
- Select inherited mechanisms by demonstrated usefulness. A feature built in
  one application still needs integration and evaluation in another.

Anchor construction remains a practical bridge: the retained runtime includes
qualified language profiles and prepared Python/HTML app paths. Their presence
does not establish every hosted-model or receiving-application behavior. The
program composition API supports its qualified deterministic profiles. CELL units
are defined by kernels, rather than by program profiles.

## Evidence and attribution

The heritage ledger distinguishes inspected implementation, historical receipts,
newly executed tests, and described-only concepts. The orientation adds useful
labels: **creator-reported**, **artifact-observed**, **baked in a specific
context**, and **proposed or illustrative**. A baked feature is a candidate for
reuse, not a universally integrated framework capability.

The orientation attributes Baking to the creator's development practice and
Raven's elaboration of it, and attributes Chase's origin to Raven according to
the creator. This repository preserves that attribution as reported history;
it separately identifies the inspected Chase implementation and its test scope.
Different Hermes integration lineages likewise remain distinct; no generic
compiler label stands in for a complete host application.

## Directions requiring separate qualification

The orientation describes an AppAI heartbeat and a persisted plan for a later
wake. An optional activation profile could combine a configurable schedule,
events, resource bounds, and comparisons of prior expectations with observations.
This release has no new universal scheduler, predictive controller, or claim of
tested Android integration. Earlier Chromo memory and later Chroma designs also
remain distinct until their source formats and contracts are qualified.

The resident milestone now supplies bounded foreground activation, eight actual
Hermes connections, and portable representative Engrams with local mission
policy. These concrete examples do not make all Bio-Software an AppAI: that
designation requires integration as a host's autonomic nervous system, with
the whole host as SELF and its installation as NEST.

Broader host assimilation, richer constructive Engrams, additional kernels and execution profiles,
and swarm coordination can grow from this work. Each needs its own source,
authority boundary, bounded failure behavior, and current tests before joining
the supported capability list.

## KPP and the creator's clarification

KPP is the preferred development practice, supported by protocol tooling.
Recipe/3 and explicitly bound recipe/4 obligations apply the shared Anchors;
unbound recipe/4 obligations are generic requirements. Recipe language choices
and construction techniques are explicit decisions, independent of evidence.
The Baker may be human, AI, or collaborative; a Taster evaluates while the Baker
retains responsibility. Explicit host permissions still govern admission.

## Selective augmentation and research objectives

Evaluate preserving a mature host and adding selected sensory/motor pathways
before attempting wholesale conversion. The creator reports practical complexity
limits in earlier Anchor experiments; this is research context, not a universal
measured ceiling. A bounded synthetic example tests shared native functions,
optional MIND failure, explicit grants, source retention and append-history.

MantleOS aims to multiply available intelligence's practical capability through
its Body, memory and interfaces. This is a research hypothesis; this release
provides no model ranking or live comparative measurement. AppAI residence,
portable Engram continuity and carrier format are distinct. Existing representative
missions preserve a separate child's identity and experience; returned findings
await review and append-only admission. Founding PRIMER inheritance grants no
authority and does not copy the parent identity.

Logical append-only history preserves previous records across later publications.
Rewriting a PNG/cartridge to carry that history is not physically immutable storage.
Repeatable pinned builds and repeatable AI construction workflows are different
claims; neither an accepted artifact nor a hash proves all future reproductions.
